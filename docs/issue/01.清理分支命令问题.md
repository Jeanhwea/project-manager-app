# 清理分支命令问题

## 问题描述
下面这个命令存在问题
```
pma c
```

就是我 origin 的 aaa 分支在远端已经删除了，运行 pma c 它没有同步清理掉本地的 origin/aaa

## 预期目标

本文档涉及的预期目标从三个维度分层梳理：

> **功能目标** — 命令"做什么"，即正确识别并清理废弃分支
> **健壮性目标** — 命令"不出错"，即边界情况下的正确行为与容错
> **体验目标** — 命令"用得好"，即交互反馈、安全预览、操作信心

---

### 🎯 功能目标

#### F1. 核心目标：同步清理远端已删除的跟踪分支（D 类分支）

- **当前问题**：远端的分支（如 `origin/aaa`）已在远端被删除，但本地运行 `pma c` 后，`refs/remotes/origin/aaa` 没有同步删除，导致本地遗留了大量的废弃远端跟踪分支。
- **预期表现**：`pma c` 应当能识别上述场景，并用 `git remote prune origin` 清理掉本地已经不存在对应远端分支的 tracking ref。

#### F2. 分支分类逻辑确认

`pma c` 内部将分支分为四类，本次问题聚焦于 D 类：

| 类别 | 定义 | 当前行为 | 预期行为 |
|------|------|---------|---------|
| **A 类** | 保护分支（master/main/develop/dev） | 永远不删 | ✅ 正确 |
| **B 类** | 本地存在但未合并到保护分支的分支 | 仅加 `-D` 时强制删除 | ✅ 正确 |
| **C 类** | 本地存在且已合并到保护分支的分支 | 始终删除（本地+远端） | ✅ 正确 |
| **D 类** | 远端孤儿分支 — 本地没有跟踪分支的远端分支 | 已实现通过 `git ls-remote` 检测并删除 | ✅ 已实现，但问题中所提场景未覆盖 |

**本次修复需要额外确认**：
- `local_tracking` 集合的计算逻辑是否覆盖了"本地分支已删除、但 tracking ref 仍残留"的情况
- `git remote prune origin` 是否在每次 `pma c` 时都被正确触发（当前代码在 plan 函数末尾有 `PruneRemote` 阶段，需验证该阶段是否被正确触发）

#### F3. 场景补充：本地存在 tracking ref 但远端已删除

当前 D 类分支的逻辑是：通过 `git ls-remote --heads <remote>` 获取远端真实存在的分支列表，与本地 tracking ref 列表对比，找出本地有跟踪但远端已不存在的分支。

**问题场景的具体流程**：
1. 用户本地分支 `aaa` 被删除（或已切换），但 `refs/remotes/origin/aaa` 这个 tracking ref 仍然存在
2. 远端 `origin/aaa` 已经被别人删除
3. 运行 `pma c` 后，`ls-remote` 不会返回 `aaa`（远端已删），且 `aaa` 不在 protected 分支列表中
4. 此时 `aaa` 没有本地的跟踪分支（因为本地分支 `aaa` 已删除），会被归入 D 类
5. **预期**：`pma c` 应检测到这种场景并执行 `DeleteRemoteBranch` + `PruneRemote` 清理

**需要验证/修复的点**：
- [ ] 确认 `local_tracking` 集合是否覆盖了本地无对应分支但远端 tracking ref 仍残留的情况
- [ ] 确认 `git remote prune origin` 是否在每次 `pma c` 时都正确执行（当前代码在 plan 函数末尾有 `PruneRemote` 阶段，需要验证该阶段是否被正确触发）

#### F4. 用户故事的额外场景

除了上述场景，还应覆盖以下用户故事：

##### F4.1 场景 A：本地分支已删除，远端也已删除
```
git branch -d aaa              # 本地已删除
git push origin --delete aaa   # 远端已删除
# 此时 refs/remotes/origin/aaa 残留
λ pma c → 应清理 origin/aaa tracking ref
```

##### F4.2 场景 B：本地分支仍在，但远端已删除
```
# 本地还有 aaa 分支（未切走），远端 aaa 已被删除
λ pma c
```
- **预期**：`aaa` 是 B 类分支（未合并），仅加 `-D` 才清理本地分支；但 **tracking ref 应通过 prune 清理**
- 需要确保此时即使本地分支存在，`origin/aaa` 这个 tracking ref 也能被清除

##### F4.3 场景 C：多 remote 下的孤儿分支清理
```
# 有 origin 和 upstream 两个 remote
# upstream/aaa 在远端已删除
λ pma c
```
- **预期**：所有 remote 的孤儿分支都应被清理，不应遗漏

### 🛡️ 健壮性目标

#### R1. 增量执行与幂等性

- `pma c` 在已清理干净的分支列表上再次执行时，不应报错，也不应产生任何误删除操作
- 连续多次执行 `pma c`，效果应与单次执行一致（幂等）
- 在多 remote 场景下，每个 remote 的 prune 操作彼此独立，一个 remote 的失败不应阻塞其他 remote 的清理

#### R2. 保护分支零误删保障

- 保护分支（master/main/develop/dev）的本地分支、本地 tracking ref 必须**在任何情况下不被删除**，包括：
  - 保护分支的 tracking ref 即使远端不存在，也不应被 prune 清除（例如主分支被管理员误删远端，本地仍应保留 tracking ref）
  - 用户自定义的保护分支配置应当生效
- 需要明确保护分支是否应排除在 prune 范围之外，如果是，则需要在 `git remote prune` 的 prune 行为外额外做一层安全过滤

#### R3. 错误处理与降级

- 断网或 remote 不可达时：`git ls-remote` 失败应优雅降级，跳过该 remote 的 D 类分支检测并给出提示，不应阻塞 C 类、B 类分支的清理
- `git remote prune` 执行失败时：应明确报告哪个 remote 的 prune 失败，以便用户手动处理
- 单个仓库的清理失败不应阻塞多仓库模式的后续仓库处理

#### R4. 多仓库兼容性

- `pma` 支持多仓库模式（如 `pma c` 在多个项目目录下依次执行），各仓库的 remote 配置可能不同，需要确保每个仓库独立执行上述逻辑

### 💡 体验目标

#### E1. Dry-Run 预览能力

当前 `pma c --dry-run` 已实现，但应确保 dry-run 模式下能清晰展示 D 类分支的清理计划，包括：
- 将要删除的远端跟踪分支列表（按 remote 分组）
- 每个 tracking ref 对应的远端已删除分支名
- 本次 dry-run 的统计摘要（多少条 tracking ref 将被清理）

#### E2. 清理结果反馈

清理完成后应输出结构化反馈，让用户清晰感知到效果：
```
<== 分支清理完成 (状态: 清理后)
    C 类 (已合并分支): 删除 2 条   → feature/log, bugfix/pay
    D 类 (孤儿分支):   清除 3 条   → origin/aaa, origin/old-feature, upstream/archived
    B 类 (未合并分支):  保留 1 条   → feature/experiment (需 -D 强制删除)
    A 类 (保护分支):    跳过 4 条   → master, dev, main, develop
<== 执行耗时: 1.2s
```

#### E3. 决策透明性

- 对于 D 类分支，建议输出"判断依据"，让用户了解为何某分支被判定为孤儿分支
  - 例如：`origin/aaa → ls-remote 未返回，本地分支 aaa 不存在，分类为 D 类，已清理`
- 对于保护分支的 tracking ref 跳过清理时，也应给出提示

#### E4. 保护机制

- 运行 `pma c` 前，对于将要删除的 D 类分支数量超过阈值（例如 > 10 条）时，应提示用户确认后再执行
- 确认提示应列出所有将删除的 tracking ref 列表，避免批量误删
