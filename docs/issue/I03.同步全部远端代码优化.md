# I03. 同步全部远端代码优化

> 同步全部远端（`pma s -a`）时，若某个本地分支在远端已被清理，会导致整个同步命令执行失败。本文将其整理为背景 → 现状 → 差距 → 路径 → 开放问题 → 结论，并给出修复方向。

## 背景

`pma s -a`（`sync --all`）用于"同步全部远端"：在一个仓库内遍历所有本地分支，并依次从每个配置的 remote（如 `gitana`、`origin`）拉取同名分支代码，将远端更新一次性同步到本地。

一个仓库通常配置了多个 remote（示例仓库 `final-ai-report` 同时配置了 `gitana` 与 `origin`）。`pma s -a` 会对每一个 `(本地分支, remote)` 组合执行 `git checkout <branch>` + `git pull <remote> <branch>`，完成全量同步。

## 现状

当前实现按"分支 → remote"逐个执行 `git pull`，任意一次 pull 失败即以非零退出码终止整个命令，后续分支与 remotes 的同步全部被跳过。

以下为真实失败现场（执行 `pma s -a`）：

```text
➜  final-ai-report git:(master) pma s -a

[1/1] /home/jhh/code/mtiisl/chx/final-ai-report

## ▸ 同步其他分支
==> git checkout dev
Switched to branch 'dev'
Your branch is up to date with 'origin/dev'.
==> git pull gitana dev
From gitana.jeanhwea.io:mtiisl/llm/final-ai-report
 * branch            dev        -> FETCH_HEAD
Already up to date.
==> git checkout dev
Already on 'dev'
Your branch is up to date with 'origin/dev'.
==> git pull origin dev
From ssh://192.168.0.110:2222/chx/aizx/final-ai-report
 * branch            dev        -> FETCH_HEAD
Already up to date.
==> git checkout fix/M-lang
Switched to branch 'fix/M-lang'
==> git pull gitana fix/M-lang
fatal: couldn't find remote ref fix/M-lang
<== 执行失败: Git command exited with code 1
➜  final-ai-report git:(fix/M-lang) git checkout master
Switched to branch 'master'
```

正常分支（如 `dev`）在所有 remote 上都能成功 pull；但 `fix/M-lang` 在 `gitana` 远端已被清理（ref 不存在），`git pull gitana fix/M-lang` 直接 `fatal: couldn't find remote ref fix/M-lang`，命令整体失败。

## 差距

1. **缺乏容错，单点失败导致整体中断**：当某本地分支在某 remote 上已被删除，对应的 `git pull <remote> <branch>` 会 fatal 退出，整个 `pma s -a` 立即中止，后续分支与 remotes 的同步全部被跳过。
2. **没有"跳过缺失 ref"的降级逻辑**：理想情况下应识别"远端已无此分支"并跳过，而不是让命令崩溃；当前对孤儿分支场景完全没有处理。
3. **错误影响面过大**：一次失败不仅中断流程，还把仓库留在半同步状态（`fix/M-lang` 已 checkout、后续分支未处理），用户需手动 `git checkout master` 才能恢复。
4. **缺乏汇总反馈**：命令失败后，用户无法一眼看出"哪些分支/remote 成功、哪些被跳过"，排障成本高。

## 路径（修复方案）

核心思路：**在执行 `git pull <remote> <branch>` 前先校验远端是否仍存在该分支 ref；不存在则跳过并降级为警告，继续后续同步。**

1. **ref 预校验**：对每个 `(remote, branch)` 组合，在 pull 前用 `git ls-remote --heads <remote> <branch>`（或 `git rev-parse --verify <remote>/<branch>`）确认远端存在该分支。
   - 不存在 → 跳过该组合，输出提示（如 `<== 跳过 fix/M-lang: 远端 gitana 不存在该分支(ref 已清理)`），继续下一个。
   - 存在 → 正常执行 `git pull <remote> <branch>`。
2. **失败降级**：`git pull` 仍可能因网络/权限失败，这类异常应捕获后降级为警告并继续，而非以非零码退出；可选 `--fail-fast` 开关保留"任一失败即中止"的严格模式。
3. **故障隔离**：单 remote 单分支的缺失/失败不影响其他 `(remote, branch)` 组合的同步。
4. **结束汇总**：同步完成后输出结构化统计，例如：
   ```text
   <== 同步完成
       成功: dev(gitana, origin), ...
       跳过: fix/M-lang (gitana: ref 已清理)
       失败: <none>
   ```
5. **（可选）残留 tracking ref 清理**：对"本地分支仍在、但所有 remote 均已删除该分支"的孤儿分支，结束时提示用户用 `pma c` 或 `git remote prune` 清理，而不在 `pma s -a` 主流程中强删本地分支。

## 开放问题

1. 当某本地分支在**所有** remote 都不存在时，是否应在同步结束后提示用户"该分支已成孤儿、建议删除"？
2. 是否需要 `--fail-fast` 严格模式开关，还是统一改为"容错继续"？
3. 跳过/被隔离的分支是否需要在汇总中全部列出，还是仅在计数超阈值时详细展示？
4. 是否应先用 `git remote prune <remote>` 清理本地残留 tracking ref，还是仅跳过 pull、不做清理？

## 结论

根因明确：`pma s -a` 在同步时对"远端已删除分支"缺乏容错，单点 `git pull` 失败即导致整体中断并遗留半同步状态。

建议优先落地**最小修复**：在 pull 前做 ref 预校验、对缺失 ref 跳过并降级为警告、保证单点失败不阻塞整体同步；`--fail-fast` 严格模式及孤儿分支提示作为可选增强。该修复成本低、收益高（直接消除最常见的同步中断场景），应纳入本期优化。
