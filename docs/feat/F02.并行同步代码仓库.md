# F02. 并行同步代码仓库

## 背景

`pma sync`（`pma s`）用于在指定目录下批量同步 Git 仓库（拉取当前分支、拉取标签、可选推送）。
随着管理的仓库数量增多（常见为几十到上百个），逐个串行同步的耗时线性增长——每个仓库都要经历
网络往返（fetch/pull/push），但 CPU 几乎全程空闲。机器本身是多核的，串行执行没有利用任何并行能力，
大量时间浪费在等待网络 I/O 上。

目标：在保持"每个仓库内部操作顺序正确、互不干扰"的前提下，让多个仓库的同步任务并行执行，
把总耗时从 O(仓库数 × 单仓库耗时) 降低到接近 O(单仓库耗时 × (仓库数 / 并发度))。

---

## 现状

`pma s` 的完整调用链如下：

1. `src/commands/sync.rs::run` → `commands::run_multi_repo_cmd`
2. `src/commands/multi_repo.rs::run_multi_repo_cmd` → `run_multi_repo`
3. `run_multi_repo` 用 `for (index, repo_info) in walker.repositories().iter().enumerate()`
   **逐个串行** 处理仓库，对每个仓库执行：
   - `cmd.collect(repo_path)` 收集上下文（读 git 状态、`should_push_to_remote` 内部 `ConfigManager::load_config`）
   - `cmd.plan(&ctx, repo_path)` 生成 `ExecutionPlan`（阶段：同步其他分支 → 拉取当前分支 → 拉取标签 → 推送）
   - `cmd.execute(&plan)` 执行计划
4. `src/engine/plan.rs::run_plan` 内部同样是**串行**：`for phase in plan.phases()` → `for step in phase.steps()`，
   每个 `GitOperation` 通过 `src/domain/runner/command.rs::CommandRunner::execute_streaming`
   起一个独立子进程并流式打印 stdout/stderr。
5. 输出是顺序写入终端的，顺序依赖 `index + 1`/`total` 生成形如 `[1/6] /data/code/...` 的头部，
   随后逐段打印 `▸ 拉取当前分支` 等。

当前串行执行的典型输出（来自原文档）：

```
(base) gitana:code $ pma s

[1/6] /data/code/jeanhwea/jkb

## ▸ 拉取当前分支
```

### 关键事实（来自代码，改造前必须确认）

- **仓库之间完全独立**：每个 git 操作都通过 `ExecutionContext.working_dir` 指定各自仓库路径，
  不修改全局当前目录；`resolve_walker_path` 在遍历前已把 `.` 解析为固定 cwd。
- **仓库内部有顺序依赖**：`checkout → pull` 必须先切分支再拉取；`push` 必须在 `pull` 之后。
  因此并行的安全边界是**仓库级**，不能在单个仓库的计划内部并行。
- **失败隔离已存在**：串行时单仓库出错会 `output::error_chain` 后 `continue`，不中断其它仓库。
- **git 命令本身是阻塞子进程**：`execute_streaming` 已为每条命令各起一个读线程去消费 stdout/stderr，
  父线程 `child.wait()` 阻塞。

## 差距

| 维度 | 现状 | 期望 |
|------|------|------|
| 执行模型 | 单线程，逐仓库串行 | 多仓库并发，并发度 ≈ CPU 核数 |
| 资源利用 | 多核空闲，仅 1 核在等网络 | 多个仓库同时等待网络、分摊 I/O 等待 |
| 总耗时 | 随仓库数线性增长 | 接近按并发度收敛 |
| 输出 | 顺序、可读 | 并行后天然交错，需要重新设计可读性 |
| 进度/编号 | `[i/n]` 反映执行顺序 | 执行顺序不再确定，需预分配固定编号 |
| 结果汇总 | 单线程累计 `ExecutionResult` | 需线程安全聚合（已执行数 / 错误列表） |
| 并发度控制 | 无 | 默认按 CPU 核数，最好可显式覆盖 |

风险点（差距带来的新问题）：

1. **输出交错**：多个仓库同时向 stdout 写，日志会乱成一团，无法定位某个仓库的执行结果。
2. **编号失真**：`[i/n]` 依赖顺序遍历，并行后不能再用"执行到哪"当编号。
3. **结果聚合不安全**：`ExecutionResult` 当前不是 `Send + Sync`，并行写需加锁或走 channel 汇总。
4. **网络饱和 / 远端限流**：并行 fetch/push 同一下游远端可能触发 GitHub/GitLab 限流或打满带宽。
5. **线程爆炸**：若"每仓库一线程、每 git 命令再起读线程"，浅仓库虽可控，深目录仍可能瞬时线程过多。

---

## 路径

### 1. 并发粒度：仅仓库级

保持每个仓库内部的 `checkout → pull → push` 顺序不变（仍是单线程跑完一个计划），
只在 **仓库与仓库之间** 并行。这是零状态冲突风险的边界：不同仓库工作目录彼此独立。

### 2. 并发度（degree of parallelism）

- **默认串行**：`pma s` 不传 `-j`（或 `-j 1`）时行为与现在完全一致，逐仓库串行，保证输出可读、回归无惊喜。
- 并行是**显式 opt-in**：仅当用户传入 `-j / --jobs <N>` 且 `N >= 2` 时才并行，并发度即 `N`。
- `N` 超过仓库总数时自动收敛到仓库数，且至少为 2 才进入并行；`-j 1` 强制串行。
- 为方便"吃满机器"，约定 `-j 0` 表示自动取操作系统线程数（`std::thread::available_parallelism()`，标准库、无需额外依赖）；
  但不传 `-j` 时**不会**自动并行。
- 极端高核机器如需限制，显式用 `-j` 控制。远端限流风险见开放问题。

### 3. 输出处理（核心难点）

采用"**每仓库缓冲 + 原子成块输出**"：

- 工作线程不再直接 `output::*` 打终端，而是把该仓库的全部输出（头部、`▸` 段、命令流、结果）
  写入一个本地 buffer（`String` 或 `Vec<String>`）。
- 仓库处理完成时，把整块 buffer 一次性、原子地刷到终端（加一个全局输出锁，保证一块不被打断）。
  这样既保留 `[i/n]` 头部，又不会让不同仓库的行交错。
- 预分配固定编号：在遍历 `walker.repositories()` 时先给每个仓库记 `0..n-1` 的序号，
  头部显示原始序号，与完成先后无关。
- 可选增强：`-l / --live` 实时模式，用 `[repo] ` 前缀逐行打，便于观察进度但较吵，默认关闭。

### 4. 结果聚合

- 工作线程结束时回传该仓库的 `ExecutionResult`（成功/失败、已执行数、错误列表），
  主线程用 `Mutex<ExecutionResult>` 合并，或经 `mpsc` 汇总后合并。
- 汇总信息（成功数、失败仓库名 + 原因）在所有任务结束后统一打印，作为 footer。

### 5. 实现方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. Rayon | `repositories().par_iter().for_each(...)` | 改动最小，自动 work-stealing | 需引入 rayon 依赖；输出仍需自行缓冲 |
| B. std 线程池 | 主线程把仓库路径塞进 `mpsc`，起 `degree` 个 worker 取任务、回传结果 | 零新依赖、可控、易做缓冲/汇总 | 代码量略多 |
| C. 异步运行时 | tokio 驱动 | 高并发优雅 | 项目当前是纯同步 CLI，引入 async 成本大，过度设计 |

**已确定采用方案 B（纯标准库）**：使用 `std::thread::scope` 起固定数量的工作线程（仅在 `-j >= 2` 时启用），
**不引入 rayon 等第三方依赖**；需要"吃满机器"时通过 `-j 0` 取 `std::thread::available_parallelism()`。
与现有同步、无 async runtime 的风格一致，且最便于落实"缓冲输出 + 结果汇总"。
若日后多个命令都要并行，可把线程池抽成一个小工具模块（`src/domain/runner/pool.rs`）。

### 6. 改造落点（代码级）

- `src/commands/multi_repo.rs::run_multi_repo`：把 `for` 循环改为"预分配序号 + 派发到线程池"；
  保留串行分支（`jobs <= 1` 或仓库数 <= 1 时走原逻辑，保证 `-j 1` 与历史行为一致）。
- `src/commands/sync.rs::SyncArgs`：新增 `-j/--jobs` 参数（默认 None / `1` → 串行；`>=2` 并行；`0` → 操作系统线程数）。
- `src/commands/mod.rs` / `run_multi_repo_cmd`：透传 `jobs` 到 `run_multi_repo`；
  `status`、`doctor` 等其它多仓库命令保持调用串行（`jobs` 传 1 / 不传），**本次不改造**。
- `src/utils/output.rs`：新增"缓冲收集器"与"加锁原子刷出"能力（或在工作线程内用局部 buffer）。
- `src/model/plan.rs::ExecutionResult`：确保可跨线程合并（加锁或结构化拷贝后合并）。

### 7. 影响范围（已决策）

- **仅 `sync`（`pma s`）支持并行**，但默认串行；仅当用户显式 `-j >= 2` 时才并行，`-j` 可调节。
- `status`、`doctor` 等其它多仓库命令**本次不改造**，维持串行，避免范围蔓延与回归风险。
- `dry_run` 模式天然安全，并行时同样走缓冲输出。

## 开放问题

1. **输出策略**：默认"缓冲成块、按原序统一打印"还是"实时带仓库前缀逐行输出"？是否提供 `-l/--live` 实时模式？
2. **进度呈现**：完成顺序与编号顺序不一致时，是"完成即打印该块（带原始编号）"还是"全部完成按原序统一打印"？
3. **错误可见性**：并行下单个仓库失败如何醒目提示？是否维持"末尾汇总失败清单"即可？
4. **远端限流**：并行 push 是否触发 GitHub/GitLab 限流？是否需把 push 阶段单独限流（如 push 并发 < pull 并发）？
5. **信号与取消**：运行中 `Ctrl-C` 如何同时终止 N 个子进程？是否纳入 v1，还是先吃默认行为？
6. **回归保障**：`-j 1` 是否应保证与当前串行输出逐字节一致（除编号语义外）？需补 CLI 测试。

## 结论

- `pma s` 当前在 `run_multi_repo` 中逐仓库串行执行，多核闲置、总耗时随仓库数线性增长，
  主要瓶颈是等待网络 I/O 而非计算。
- 安全的并行边界是**仓库级**：仓库内部 `checkout → pull → push` 顺序必须保持串行，
  仓库之间工作目录独立、可安全并发。
- **已决策**：默认**串行**（不传 `-j` 或 `-j 1` 与现状一致）；并行为显式 opt-in，
  仅 `-j >= 2` 启用，并发度即 `N`，`-j 0` 表示自动取操作系统线程数（`std::thread::available_parallelism()`）；
  采用**纯标准库 `std::thread::scope`**（不引入 rayon）；**仅 `sync` 改造**，
  `status`/`doctor` 维持串行，不在此次范围。
- 配合"**每仓库输出缓冲 + 原子成块刷出**"和"**线程安全的结果汇总**"解决并行带来的可读性与聚合问题。
- 改造风险低（不触碰 git 状态语义、失败隔离天然成立），预期把同步耗时按并发度显著收敛。
- 落地前仍需敲定开放问题中的输出策略、进度呈现、远端限流与 `-j 1` 回归约定。

## 实现记录（2026-10-24）

已按上述决策落地，开放问题的处置如下：

1. **输出策略**：采用"每仓库缓冲 + 完成即原子成块刷出"，不提供 `-l/--live` 实时模式（v1 不做）。
2. **进度呈现**：仓库处理完成即打印该块（带原始预分配编号 `[i/n]`），完成顺序与编号顺序不一致。
3. **错误可见性**：失败仓库在块内已有 `<== 执行失败` 红色提示，末尾"执行汇总"footer 再用红色逐行列失败清单（仓库路径 + 失败操作）。
4. **远端限流**：v1 不做 push 单独限流，由用户通过 `-j` 显式控制并发度规避。
5. **信号与取消**：v1 保持默认行为（Ctrl-C 终止进程），未做子进程组取消。
6. **`-j 1` 回归**：串行分支代码路径与改造前逐字节一致（无 footer），由 `resolve_jobs` 单测与端到端验证保障。

代码落点：

- `src/commands/sync.rs`：`SyncArgs` 新增 `-j/--jobs`（默认 1）与 `--timeout`（单仓库超时分钟数，默认 30，0 = 不限）。
- `src/commands/multi_repo.rs`：新增 `run_multi_repo_cmd_with_jobs` 入口；`jobs <= 1` 或仓库数 `<= 1` 走原串行逻辑，
  `jobs >= 2` 用 `std::thread::scope` 起 N 个工作线程 + `AtomicUsize` 取任务、预分配序号，
  `Mutex<Vec<RepoOutcome>>` 汇总，末尾打印"执行汇总"（仓库成功数 / 操作数 / 失败与跳过清单）。
- `src/utils/output.rs`：新增线程本地输出收集器（`capture_start` / `capture_finish` / `current_sink` / `emit_line`）
  与全局锁原子刷出（`flush_block`）；`src/domain/runner/command.rs` 的流式读线程继承工作线程的收集器。
- `src/model/plan.rs`：`ExecutionResult::merge` 支持跨线程结果合并。

## 增量实现记录（2026-10-24 晚）

并行输出统计与同步超时：

- **进度输出**：并行模式开始打印 `并行同步开始: N 个仓库, 并发度 J`；每个仓库块刷出前打印
  `进度 done/total · 进行中 K · 剩余 M`（`SyncProgress` 原子计数器：begin/complete/in_flight），
  串行模式不打印任何进度行，保持历史输出不变。
- **同步超时**：每个仓库自 execute 起算默认 30 分钟 deadline（`--timeout` 覆盖，0 = 不限）；
  `engine/plan.rs::run_plan_with_deadline` 在步骤间检查 deadline，超时则记 `同步超时` 错误并跳过剩余操作；
  单条流式 git 命令的超时值为 deadline 剩余预算，`CommandRunner::execute_streaming` 轮询 `try_wait`，
  超时后杀进程树（Windows `taskkill /F /T`，Unix `kill`）并返回 `AppError::Timeout`，
  该仓库标记失败（footer 原因带 `(超时)`），不影响其它仓库。
- 超时只覆盖计划执行阶段的流式 git 操作（pull/fetch/push/checkout 等网络操作）；
  collect 阶段均为本地 git 读取，不涉及网络，未纳入超时范围。

## 增量实现记录（2026-10-24 深夜）：汇总总耗时

- 并行模式的"执行汇总"新增 `耗时` 一行：`run_parallel` 在 `parallel_start` 前记录 `Instant`，
  scope 结束后以 `started.elapsed()` 传入 `print_summary`，用 `utils::format_duration` 打印
  （`< 60s` 显示秒；整分钟显示"X 分钟"；其余显示"X 分 Y 秒"）。
- 串行模式无汇总 footer，输出保持历史逐字节一致。
