# F02. 并行同步代码仓库

## 背景

`pma sync`（`pma s`）用于在指定目录下批量同步 Git 仓库（拉取当前分支、拉取标签、可选推送）。
随着管理的仓库数量增多（常见为几十到上百个），逐个串行同步的耗时线性增长——每个仓库都要经历
网络往返（fetch/pull/push），但 CPU 几乎全程空闲。机器本身是多核的，串行执行没有利用任何并行能力，
大量时间浪费在等待网络 I/O 上。

目标：在保持"每个仓库内部操作顺序正确、互不干扰"的前提下，让多个仓库的同步任务并行执行，
把总耗时从 O(仓库数 × 单仓库耗时) 降低到接近 O(单仓库耗时 × (仓库数 / 并发度))。

---

## 现状

`pma s` 的完整调用链如下：

1. `src/commands/sync.rs::run` → `commands::run_multi_repo_cmd`
2. `src/commands/multi_repo.rs::run_multi_repo_cmd` → `run_multi_repo`
3. `run_multi_repo` 用 `for (index, repo_info) in walker.repositories().iter().enumerate()`
   **逐个串行** 处理仓库，对每个仓库执行：
   - `cmd.collect(repo_path)` 收集上下文（读 git 状态、`should_push_to_remote` 内部 `ConfigManager::load_config`）
   - `cmd.plan(&ctx, repo_path)` 生成 `ExecutionPlan`（阶段：同步其他分支 → 拉取当前分支 → 拉取标签 → 推送）
   - `cmd.execute(&plan)` 执行计划
4. `src/engine/plan.rs::run_plan` 内部同样是**串行**：`for phase in plan.phases()` → `for step in phase.steps()`，
   每个 `GitOperation` 通过 `src/domain/runner/command.rs::CommandRunner::execute_streaming`
   起一个独立子进程并流式打印 stdout/stderr。
5. 输出是顺序写入终端的，顺序依赖 `index + 1`/`total` 生成形如 `[1/6] /data/code/...` 的头部，
   随后逐段打印 `▸ 拉取当前分支` 等。

当前串行执行的典型输出（来自原文档）：

```
(base) gitana:code $ pma s

[1/6] /data/code/jeanhwea/jkb

## ▸ 拉取当前分支
```

### 关键事实（来自代码，改造前必须确认）

- **仓库之间完全独立**：每个 git 操作都通过 `ExecutionContext.working_dir` 指定各自仓库路径，
  不修改全局当前目录；`resolve_walker_path` 在遍历前已把 `.` 解析为固定 cwd。
- **仓库内部有顺序依赖**：`checkout → pull` 必须先切分支再拉取；`push` 必须在 `pull` 之后。
  因此并行的安全边界是**仓库级**，不能在单个仓库的计划内部并行。
- **失败隔离已存在**：串行时单仓库出错会 `output::error_chain` 后 `continue`，不中断其它仓库。
- **git 命令本身是阻塞子进程**：`execute_streaming` 已为每条命令各起一个读线程去消费 stdout/stderr，
  父线程 `child.wait()` 阻塞。

## 差距

| 维度 | 现状 | 期望 |
|------|------|------|
| 执行模型 | 单线程，逐仓库串行 | 多仓库并发，并发度 ≈ CPU 核数 |
| 资源利用 | 多核空闲，仅 1 核在等网络 | 多个仓库同时等待网络、分摊 I/O 等待 |
| 总耗时 | 随仓库数线性增长 | 接近按并发度收敛 |
| 输出 | 顺序、可读 | 并行后天然交错，需要重新设计可读性 |
| 进度/编号 | `[i/n]` 反映执行顺序 | 执行顺序不再确定，需预分配固定编号 |
| 结果汇总 | 单线程累计 `ExecutionResult` | 需线程安全聚合（已执行数 / 错误列表） |
| 并发度控制 | 无 | 默认按 CPU 核数，最好可显式覆盖 |

风险点（差距带来的新问题）：

1. **输出交错**：多个仓库同时向 stdout 写，日志会乱成一团，无法定位某个仓库的执行结果。
2. **编号失真**：`[i/n]` 依赖顺序遍历，并行后不能再用"执行到哪"当编号。
3. **结果聚合不安全**：`ExecutionResult` 当前不是 `Send + Sync`，并行写需加锁或走 channel 汇总。
4. **网络饱和 / 远端限流**：并行 fetch/push 同一下游远端可能触发 GitHub/GitLab 限流或打满带宽。
5. **线程爆炸**：若"每仓库一线程、每 git 命令再起读线程"，浅仓库虽可控，深目录仍可能瞬时线程过多。

---

## 路径

### 1. 并发粒度：仅仓库级

保持每个仓库内部的 `checkout → pull → push` 顺序不变（仍是单线程跑完一个计划），
只在 **仓库与仓库之间** 并行。这是零状态冲突风险的边界：不同仓库工作目录彼此独立。

### 2. 并发度（degree of parallelism）

- 默认 `degree = num_cpus::get()`（物理/逻辑核数）。
- 提供 CLI 覆盖：`-j / --jobs <N>`，`0` 或不传时回退到 CPU 核数；`-j 1` 等价于当前串行行为（便于回归）。
- 设软上限（如 `min(degree, 8)`）避免海量并行把单远端打挂，具体上限作为开放问题确认。

### 3. 输出处理（核心难点）

采用"**每仓库缓冲 + 原子成块输出**"：

- 工作线程不再直接 `output::*` 打终端，而是把该仓库的全部输出（头部、`▸` 段、命令流、结果）
  写入一个本地 buffer（`String` 或 `Vec<String>`）。
- 仓库处理完成时，把整块 buffer 一次性、原子地刷到终端（加一个全局输出锁，保证一块不被打断）。
  这样既保留 `[i/n]` 头部，又不会让不同仓库的行交错。
- 预分配固定编号：在遍历 `walker.repositories()` 时先给每个仓库记 `0..n-1` 的序号，
  头部显示原始序号，与完成先后无关。
- 可选增强：`-l / --live` 实时模式，用 `[repo] ` 前缀逐行打，便于观察进度但较吵，默认关闭。

### 4. 结果聚合

- 工作线程结束时回传该仓库的 `ExecutionResult`（成功/失败、已执行数、错误列表），
  主线程用 `Mutex<ExecutionResult>` 合并，或经 `mpsc` 汇总后合并。
- 汇总信息（成功数、失败仓库名 + 原因）在所有任务结束后统一打印，作为 footer。

### 5. 实现方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. Rayon | `repositories().par_iter().for_each(...)` | 改动最小，自动 work-stealing | 需引入 rayon 依赖；输出仍需自行缓冲 |
| B. std 线程池 | 主线程把仓库路径塞进 `mpsc`，起 `degree` 个 worker 取任务、回传结果 | 零新依赖、可控、易做缓冲/汇总 | 代码量略多 |
| C. 异步运行时 | tokio 驱动 | 高并发优雅 | 项目当前是纯同步 CLI，引入 async 成本大，过度设计 |

**推荐 B**：与现有同步、无 runtime 的风格一致，不引入重依赖，且最便于落实"缓冲输出 + 结果汇总"。
若日后多个命令都要并行，可把线程池抽成一个小工具模块（`src/domain/runner/pool.rs`）。

### 6. 改造落点（代码级）

- `src/commands/multi_repo.rs::run_multi_repo`：把 `for` 循环改为"预分配序号 + 派发到线程池"。
- `src/commands/mod.rs` 或相关 `run_multi_repo_cmd`：新增 `-j/--jobs` 参数，透传到 `run_multi_repo`。
- `src/utils/output.rs`：新增"缓冲收集器"与"加锁原子刷出"能力（或在工作线程内用局部 buffer）。
- `src/model/plan.rs::ExecutionResult`：确保可跨线程合并（加锁或结构化拷贝后合并）。
- 仅 `sync` 默认开启并行；`dry_run` 模式天然安全可直接并行。

## 开放问题

1. **并发度上限**：默认 CPU 核数是否足够？是否需要额外的网络/远端维度上限（如 push 限到 4 并发）？
2. **输出策略**：默认"缓冲成块"还是默认"实时带仓库前缀"？`-l` 实时模式是否纳入 v1？
3. **进度呈现**：完成顺序与编号顺序不一致时，是否需要"完成即打印该块（带原始编号）"，还是"全部完成按原序统一打印"？
4. **错误可见性**：并行下单个仓库失败如何醒目提示？是否维持"末尾汇总失败清单"即可？
5. **远端限流**：并行 push 是否会触发 GitHub/GitLab 限流？是否需要把 push 阶段单独限流？
6. **影响范围**：本次只改 `sync`，还是 `status`/`doctor` 也一并并行？（建议先只动 `sync`，验证稳定后再推广。）
7. **信号与取消**：运行中 `Ctrl-C` 时如何同时终止 N 个子进程？是否纳入 v1，还是先吃默认行为？
8. **是否引入依赖**：rayon（方案 A）还是纯 std（方案 B）？倾向 B，但需确认。
9. **回归保障**：`-j 1` 是否应保证与当前串行输出逐字节一致（除编号语义外）？需补 CLI 测试。

---

## 结论

- `pma s` 当前在 `run_multi_repo` 中逐仓库串行执行，多核闲置、总耗时随仓库数线性增长，
  主要瓶颈是等待网络 I/O 而非计算。
- 安全的并行边界是**仓库级**：仓库内部 `checkout → pull → push` 顺序必须保持串行，
  仓库之间工作目录独立、可安全并发。
- 建议采用**方案 B（std 线程池，并发度默认 = CPU 核数，支持 `-j` 覆盖）**，
  配合"**每仓库输出缓冲 + 原子成块刷出**"和"**线程安全的结果汇总**"来解决并行带来的可读性与聚合问题。
- 该改造风险低（不触碰 git 状态语义、失败隔离天然成立），预期可把同步耗时按并发度显著收敛；
  建议先仅在 `sync` 落地，验证稳定后再考虑推广到 `status`/`doctor`。
- 落地前需先敲定开放问题中的并发度上限、输出策略与 `-j 1` 回归约定。
