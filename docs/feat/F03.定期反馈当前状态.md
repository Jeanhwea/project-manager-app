# F03. 定期反馈当前状态

## 背景

`pma sync`（`pma s`）在同步过程中会显示一个进度条来反映同步进度，但进度条只展示了"已完成多少仓库"这一单一维度。当同步任务耗时较长时，用户无法了解：

- 是否有仓库同步耗时异常（接近超时或已超时）
- 是否有仓库同步失败、失败原因是什么

用户需要在不中断同步过程的前提下，定期获得这些异常状态信息，以便及时发现问题并介入处理。正常执行的仓库无需反馈，避免信息干扰。

---

## 现状

当前 `pma sync` 的输出机制如下：

1. **串行模式**（`-j 1`）：逐仓库顺序执行，每个仓库的输出块依次打印，用户可以看到每个仓库的实时执行情况。
2. **并行模式**（`-j >= 2`）：采用"每仓库缓冲 + 完成即原子成块刷出"策略，仓库处理完成时一次性打印该仓库的完整输出块。
   - 并行模式下，用户只能看到**已完成**仓库的输出，无法看到**正在执行中**的仓库的实时状态。
   - 进度条仅显示 `done/total` 的计数，不包含仓库名称、同步时间、失败信息等细节。
3. **同步超时**：每个仓库有默认 30 分钟的 deadline（`--timeout` 覆盖），超时后该仓库标记失败并跳过剩余操作，但超时信息仅在最终汇总中体现。

### 关键事实

- 并行模式下，工作线程在仓库处理完成前不会向终端输出任何信息（全部缓冲在本地 buffer 中）。
- 进度条通过 `SyncProgress` 原子计数器维护 `done` / `total` / `in_flight` 三个数值，不包含仓库标识。
- 失败信息仅在仓库处理完成后随输出块打印，并在最终"执行汇总"中列出失败清单。
- 超时信息在仓库超时后标记失败，同样仅在最终汇总中体现。

---

## 差距

| 维度 | 现状 | 期望 |
|------|------|------|
| 进度信息 | 仅显示 `done/total` 数字 | 显示仓库名称 + 同步时间 + 状态 |
| 耗时异常反馈 | 仅在最终汇总中体现超时 | 定期主动反馈耗时过长的仓库（名称 + 已同步时间） |
| 失败反馈 | 仅在仓库完成或最终汇总时告知 | 失败发生时立即或定期反馈，便于排查 |
| 信息粒度 | 无仓库级状态 | 每个正在同步的仓库的名称、已耗时、当前阶段 |
| 反馈时机 | 仓库完成时一次性输出 | 定期（如每 N 秒）输出一次当前状态快照 |

---

## 路径

### 1. 定期状态快照

在并行模式下，增加一个**定时器线程**（或主线程中的定时检查），每隔固定间隔（如 10 秒）输出一次当前所有正在同步仓库的状态快照。

状态快照包含：
- 每个正在同步的仓库的**名称**（仓库目录名或路径）
- 每个仓库的**已同步时间**（从该仓库开始执行到当前时刻的耗时）
- 每个仓库的**当前阶段**（如"拉取当前分支"、"拉取标签"、"推送"等）

### 2. 耗时异常仓库的主动反馈

在状态快照中，对**已同步时间超过阈值**的仓库进行特殊标记（如颜色高亮或附加 `(耗时过长)` 标签）。

阈值定义：
- 默认阈值：可配置（如 5 分钟），超过该阈值的仓库在快照中高亮显示。
- 超时阈值：接近 `--timeout` 设定值（如剩余时间不足 5 分钟）时，标记为 `(接近超时)`。

### 3. 失败仓库的即时反馈

当某个仓库同步失败时，不再等到最终汇总才告知用户，而是在失败发生时：
- 在下一个状态快照中立即体现该仓库的失败信息（仓库名称 + 失败原因）。
- 或者，在失败发生时立即输出一条独立的失败通知行（带 `[失败]` 前缀），不等待定时快照。

### 4. 输出格式

状态快照的示例输出格式：

```
── 同步状态 (10s) ──────────────────────
  repo-a       45s  拉取当前分支
  repo-b       32s  拉取标签
  repo-c       12s  推送
  repo-d       78s  拉取当前分支  (耗时过长)
────────────────────────────────────────
```

失败通知的示例输出格式：

```
[失败] repo-e: 同步超时 (已同步 31 分钟)
```

### 5. 实现方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 主线程定时打印 | 主线程在 `scope` 外起一个循环，每隔 N 秒读取工作线程的共享状态并打印 | 实现简单，不增加线程 | 主线程被定时循环占用；输出时机与工作线程完成刷出可能冲突 |
| B. 独立定时器线程 | 起一个独立线程，每隔 N 秒加锁读取 `Arc<Mutex<Vec<WorkerStatus>>>` 并打印快照 | 与工作线程完全解耦 | 多一个线程；需处理线程退出同步 |
| C. 工作线程主动上报 | 每个工作线程在每步操作完成后更新共享状态，主线程在空闲时检查并打印 | 状态实时性最好 | 实现复杂度较高 |

**推荐方案 B（独立定时器线程）**：与现有架构一致（`std::thread`），职责清晰，定时器线程只负责读取共享状态并打印，不干扰工作线程的执行。

### 6. 改造落点（代码级）

- `src/commands/multi_repo.rs`：在 `run_parallel` 中新增定时器线程逻辑；定义共享状态结构 `WorkerStatus`（仓库名、开始时间、当前阶段、是否失败、失败原因）。
- `src/domain/runner/command.rs` 或 `src/engine/plan.rs`：工作线程在执行过程中更新共享状态（当前阶段、进度等）。
- `src/utils/output.rs`：新增状态快照格式化输出函数。
- `src/commands/sync.rs`：`SyncArgs` 可新增 `--status-interval` 参数（状态快照间隔秒数，默认 10，0 = 关闭定期反馈）。

### 7. 影响范围

- **仅并行模式**（`-j >= 2`）支持定期状态反馈，串行模式保持现有行为不变。
- 定期反馈**不影响**现有的输出缓冲和原子刷出机制——状态快照由定时器线程直接输出，不经过仓库输出缓冲。
- 失败通知可独立于状态快照输出，也可合并到下一次状态快照中。

---

## 开放问题

1. **状态快照间隔**：默认间隔设为多少合适？10 秒是否太频繁或太稀疏？是否提供 `--status-interval` 参数让用户自定义？
2. **耗时过长阈值**：默认阈值设为多少？5 分钟？10 分钟？是否与 `--timeout` 联动（如 `timeout * 0.2`）？
3. **失败通知方式**：失败是立即输出独立通知行，还是等到下一次状态快照中体现？前者实时性好但可能打断输出，后者延迟高但输出整洁。
4. **状态快照的显示位置**：快照是覆盖前一次快照（类似进度条刷新），还是追加新行？追加行会导致终端输出膨胀，覆盖则更简洁但实现复杂（需要 ANSI 控制码）。
5. **串行模式是否也需要**：串行模式下用户已经能看到每个仓库的实时输出，定期反馈的必要性较低。但如果有大量仓库串行执行，用户也可能希望了解整体进度。
6. **仓库当前阶段的获取**：工作线程在执行过程中如何暴露"当前阶段"信息？需要在 `ExecutionPlan` 的执行循环中埋点更新共享状态。

---

## 结论

- `pma sync` 并行模式下，用户只能看到已完成仓库的输出和最终汇总，无法在同步过程中了解正在执行的仓库的状态。
- 需要增加**定期状态快照**机制，在并行模式下每隔固定间隔输出当前正在同步的仓库的名称、已耗时和当前阶段。
- 对**耗时过长**（超过阈值）和**接近超时**的仓库进行特殊标记，主动提醒用户。
- **失败仓库**的信息应在失败发生时或下一次快照中及时体现，便于用户排查问题。
- 推荐采用**独立定时器线程**（方案 B）实现，与现有架构一致，职责清晰。
- 串行模式保持现有行为不变，不做改造。
- 落地前需敲定状态快照间隔、耗时阈值、失败通知方式、快照显示位置等细节。
